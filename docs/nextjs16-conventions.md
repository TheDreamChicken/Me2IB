# Next.js 16.2.10 conventions cheat-sheet

Generated from the bundled docs in node_modules/next/dist/docs. Trust this over prior Next.js knowledge.

## routing-structure

### Differences from Next.js 13/14/15 (as trained)

- **`middleware.ts` is replaced by `proxy.ts`** — the top-level files table lists `proxy.ts` as the "Next.js request proxy". Do not create `middleware.ts`; create `proxy.ts` at the project root (or `src/`).
- **Async request APIs are mandatory**: `params` and `searchParams` are **Promises** and must be `await`ed. Signatures: `params: Promise<{ slug: string }>`, `searchParams: Promise<{ [key: string]: string | string[] | undefined }>`. Pages/layouts that read them must be `async`.
- **New global typed props helpers**: `PageProps<'/route/[param]'>` and `LayoutProps<'/route'>` are **globally available, no import required**, generated by `next dev`, `next build`, or the new `next typegen` CLI command. Static routes resolve `params` to `{}`.
- **New upgrade command**: `npx next upgrade` (Next >= 16.1.0). Pre-16.1.0: `npx @next/codemod@canary upgrade latest`.
- **Auth interrupts are canary-only**: `forbidden()`, `unauthorized()`, `forbidden.js`, `unauthorized.js`, and the `authInterrupts` config are **only in canary** — do not use them on stable 16.2.x. Handle 401/403 with `redirect()` or custom UI instead.
- **New hook** `useLinkStatus()` from `next/link` — `const { pending } = useLinkStatus()` for pending-navigation indicators (client component).
- Docs hint (verbatim from docs): "To ensure client-side navigations are instant, export `unstable_instant` from the route in addition to using Suspense." (see `docs/01-app/02-guides/instant-navigation.mdx`).
- Prefetching: dynamic routes are **skipped or only partially prefetched** unless `loading.tsx` exists; `prefetch={false}` opts out; `prefetch={active ? null : false}` enables hover-only prefetch.
- Version guides exist for v14/v15/v16 upgrades at `app/guides/upgrading/version-16` etc. in the bundled docs.

### File conventions (app router)

| File | Purpose |
|---|---|
| `layout.tsx` | Shared UI; root layout required, must render `<html>` + `<body>` |
| `page.tsx` | Makes a route public |
| `loading.tsx` | Suspense fallback; enables partial prefetch of dynamic routes |
| `error.tsx` / `global-error.tsx` | Error boundaries |
| `not-found.tsx` | Not-found UI |
| `route.ts` | API endpoint (route handler) |
| `template.tsx` | Re-rendered layout |
| `default.tsx` | Parallel route fallback |
| `proxy.ts` (root) | Request proxy (replaces middleware) |
| `instrumentation.ts` (root) | OpenTelemetry/instrumentation |

Render hierarchy: `layout` → `template` → `error` → `loading` → `not-found` → `page`/nested `layout`.

Routing patterns: `[slug]` dynamic, `[...slug]` catch-all, `[[...slug]]` optional catch-all, `(group)` route group (no URL segment; use for e.g. `(auth)` vs `(dashboard)` layouts, or multiple root layouts — remove top-level layout and give each group its own `<html>/<body>` layout), `_folder` private (non-routable), `@slot` parallel routes, `(.)`/`(..)`/`(...)` interception. A folder only becomes a route when it contains `page` or `route`. Env files: `.env`, `.env.local`, `.env.development`, `.env.production`.

### Copy-pasteable patterns

**Root layout (required):**
```tsx
// app/layout.tsx
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body><main>{children}</main></body>
    </html>
  )
}
```

**Nested layout (typed, no import needed):**
```tsx
// app/dashboard/layout.tsx
export default function Layout(props: LayoutProps<'/dashboard'>) {
  return <section>{props.children}</section>
}
```

**Server component page with data fetching:**
```tsx
// app/blog/page.tsx
export default async function Page() {
  const posts = await getPosts()
  return <ul>{posts.map((p) => <li key={p.id}>{p.title}</li>)}</ul>
}
```

**Dynamic route — params is a Promise, MUST await:**
```tsx
// app/blog/[slug]/page.tsx
export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params
  const post = await getPost(slug)
  return <h1>{post.title}</h1>
}
// or with the global helper:
export default async function Page(props: PageProps<'/blog/[slug]'>) {
  const { slug } = await props.params
  return <h1>{slug}</h1>
}
```

**searchParams — also a Promise (opts page into dynamic rendering):**
```tsx
// app/page.tsx
export default async function Page({
  searchParams,
}: {
  searchParams: Promise<{ [key: string]: string | string[] | undefined }>
}) {
  const filters = (await searchParams).filters
}
```
Rule of thumb: `searchParams` prop for server-side data loading (pagination/filtering); `useSearchParams()` hook for client-only use; `new URLSearchParams(window.location.search)` inside event handlers to avoid re-renders.

**generateStaticParams (prerender dynamic segments):**
```tsx
export async function generateStaticParams() {
  const posts = await fetch('https://.../posts').then((res) => res.json())
  return posts.map((post) => ({ slug: post.slug }))
}
```

**Loading UI (add to every dynamic route — enables partial prefetch + instant navigation):**
```tsx
// app/dashboard/loading.tsx
export default function Loading() {
  return <LoadingSkeleton />
}
```

**Navigation:**
```tsx
import Link from 'next/link'
<Link href={`/blog/${post.slug}`}>{post.title}</Link>          // prefetches in viewport
<Link prefetch={false} href="/blog">Blog</Link>                 // no prefetch
```
`useRouter` for imperative nav; native `window.history.pushState/replaceState` integrate with the router and sync with `usePathname`/`useSearchParams` (client components only).

**Pending-navigation indicator:**
```tsx
'use client'
import { useLinkStatus } from 'next/link'
export default function LoadingIndicator() {
  const { pending } = useLinkStatus()
  return <span aria-hidden className={pending ? 'is-pending' : ''} />
}
```

**Route-group layout for auth-protected app section (structure):**
```
app/
  layout.tsx            # root layout
  (auth)/login/page.tsx # public
  (app)/layout.tsx      # protected shell (check session here)
  (app)/dashboard/page.tsx
```

### Verbatim warnings / heed-this notes

- "The root layout is **required** and must contain `html` and `body` tags."
- "Using `searchParams` opts your page into **dynamic rendering** because it requires an incoming request to read the search parameters from."
- "On navigation, layouts preserve state, remain interactive, and do not rerender."
- "`<Link>` is a Client Component and must be hydrated before it can prefetch routes."
- "a route is **not publicly accessible** until a `page.js` or `route.js` file is added to a route segment."
- Canary-only feature list (do not use on stable): `forbidden`, `unauthorized`, `forbidden.js`, `unauthorized.js`, `authInterrupts`.

## auth-proxy-handlers

Next.js 16.2.10 — breaking changes vs 13/14/15, plus copy-paste patterns from the bundled docs (`authentication.md`, `16-proxy.md`, `15-route-handlers.md`).

### Breaking changes / renames vs what you knew

1. **`middleware.ts` is now `proxy.ts`.** Verbatim from docs: "Starting with Next.js 16, Middleware is now called Proxy to better reflect its purpose. The functionality remains the same."
   - File: `proxy.ts` (or `.js`) in the **project root** (or `src/`), same level as `app/`. Only ONE proxy file per project.
   - Export: either `export default function proxy(request: NextRequest)` OR named `export function proxy(request: NextRequest)`. Can be `async`. `export const config = { matcher: ... }` still works.
   - **Proxy runs on the Node.js runtime** (not Edge by default). Docs: "Proxy uses the Node.js runtime, check if your Auth library and session management library are compatible. You may need to use Middleware... if your Auth library only supports Edge Runtime" (legacy middleware docs are pinned to v15.5.6).
   - You CAN import and `await cookies()` from `next/headers` inside proxy (docs do this), or use `req.cookies.get('session')?.value`.
   - `fetch` with `options.cache`, `options.next.revalidate`, or `options.next.tags` **has no effect in Proxy**.
2. **Async request APIs are mandatory.** `cookies()`, `headers()` from `next/headers` return Promises — always `await cookies()` / `await headers()`. Sync access is gone.
3. **Route handler `params` is a Promise.** `const { id } = await ctx.params`. New globally-available `RouteContext<'/users/[id]'>` TS helper types the context param (types generated by `next dev`, `next build`, or `next typegen`).
4. **Cache Components model** for GET route handlers: they run at request time by default, may be prerendered if they touch no runtime data, and `use cache` + `cacheLife()` (from `next/cache`) caches data. **`use cache` cannot be used directly inside a Route Handler body; extract it to a helper function.**
5. Terminology: docs route "mutating-data" replaces "server actions and mutations" getting-started page; auth optimistic checks are now the "Proxy" pattern.

### proxy.ts — auth-protecting routes (optimistic cookie check only, no DB calls)

```ts
// proxy.ts  (project root — NOT middleware.ts)
import { NextRequest, NextResponse } from 'next/server'
import { decrypt } from '@/app/lib/session'
import { cookies } from 'next/headers'

const protectedRoutes = ['/dashboard']
const publicRoutes = ['/login', '/signup', '/']

export default async function proxy(req: NextRequest) {
  const path = req.nextUrl.pathname
  const isProtectedRoute = protectedRoutes.includes(path)
  const isPublicRoute = publicRoutes.includes(path)

  const cookie = (await cookies()).get('session')?.value
  const session = await decrypt(cookie)

  if (isProtectedRoute && !session?.userId) {
    return NextResponse.redirect(new URL('/login', req.nextUrl))
  }
  if (isPublicRoute && session?.userId && !req.nextUrl.pathname.startsWith('/dashboard')) {
    return NextResponse.redirect(new URL('/dashboard', req.nextUrl))
  }
  return NextResponse.next()
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|.*\\.png$).*)'],
}
```

Docs warnings (verbatim): "Proxy is _not_ intended for slow data fetching... it should not be used as a full session management or authorization solution." "since Proxy runs on every route, including prefetched routes, it's important to only read the session from the cookie (optimistic checks), and avoid database checks." "While Proxy can be useful for initial checks, it should not be your only line of defense in protecting your data." For auth, it's recommended the matcher covers all routes.

### cookies() — always async

```ts
import 'server-only'
import { cookies } from 'next/headers'

export async function createSession(userId: string) {
  const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)
  const session = await encrypt({ userId, expiresAt }) // e.g. jose SignJWT
  const cookieStore = await cookies()
  cookieStore.set('session', session, {
    httpOnly: true,
    secure: true,
    expires: expiresAt,
    sameSite: 'lax',
    path: '/',
  })
}

export async function deleteSession() {
  const cookieStore = await cookies()
  cookieStore.delete('session')
}
```

Rules: cookies must be set **on the server**; payload = minimum data (userId, role), never PII/passwords. Secret: `openssl rand -base64 32` → `.env` `SESSION_SECRET=...` → `process.env.SESSION_SECRET`.

### Data Access Layer (the canonical protection pattern — check auth near the data, NOT in layouts)

```ts
// app/lib/dal.ts
import 'server-only'
import { cache } from 'react'
import { cookies } from 'next/headers'
import { redirect } from 'next/navigation'
import { decrypt } from '@/app/lib/session'

export const verifySession = cache(async () => {
  const cookie = (await cookies()).get('session')?.value
  const session = await decrypt(cookie)
  if (!session?.userId) redirect('/login')
  return { isAuth: true, userId: session.userId }
})

export const getUser = cache(async () => {
  const session = await verifySession()
  if (!session) return null
  // query db with session.userId; return only needed columns (DTO), never whole user row
})
```

Doc guidance: layouts don't re-render on navigation (Partial Rendering), so **do NOT do auth checks in layouts** — do them in the DAL/page/leaf components. "A common pattern in SPAs is to `return null` in a layout... This pattern is **not recommended** since Next.js applications have multiple entry points." DAL protects request-time data only; static routes need Proxy. Wrap in React `cache()` to dedupe per render pass.

### Server Actions (mutations) — treat like public endpoints

```tsx
// Form: <form action={signup}> ; client uses useActionState
'use client'
import { useActionState } from 'react'
const [state, action, pending] = useActionState(signup, undefined)
// <form action={action}> ... <button disabled={pending}>
```

```ts
// app/lib/actions.ts
'use server'
import { verifySession } from '@/app/lib/dal'

export async function serverAction(formData: FormData) {
  const session = await verifySession()
  if (session?.user?.role !== 'admin') return null
  // proceed
}
```

Action signature with `useActionState`: `async function signup(state: FormState, formData: FormData)`. Validate with Zod (`safeParse`, return `{ errors: validatedFields.error.flatten().fieldErrors }` early), then create session + `redirect('/profile')`. Every Server Action must do its own auth check — client-side UI hiding is not security.

### Protected Server Component page

```tsx
// app/dashboard/page.tsx
import { verifySession } from '@/app/lib/dal'

export default async function DashboardPage() {
  const session = await verifySession() // redirects to /login if invalid
  const user = await getUserData(session.userId)
  return <h1>Welcome, {user.name}</h1>
}
```

### Route Handlers (`app/**/route.ts`)

- Methods: `GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS` (unsupported → 405). Web `Request`/`Response`, plus `NextRequest`/`NextResponse` extensions.
- **Cannot coexist with `page.js` at the same segment** (`app/page.js` + `app/route.js` = conflict; `app/page.js` + `app/api/route.js` = valid). Route handlers don't participate in layouts or client-side navigation.
- **Not cached by default.** Opt-in for GET only: `export const dynamic = 'force-static'`. Other methods never cached, even in the same file.

```ts
// app/users/[id]/route.ts — params is a PROMISE; RouteContext is global
import type { NextRequest } from 'next/server'

export async function GET(_req: NextRequest, ctx: RouteContext<'/users/[id]'>) {
  const { id } = await ctx.params
  return Response.json({ id })
}
```

```ts
// Protected route handler — two-tier check
import { verifySession } from '@/app/lib/dal'

export async function GET() {
  const session = await verifySession()
  if (!session) return new Response(null, { status: 401 })
  if (session.user.role !== 'admin') return new Response(null, { status: 403 })
  // continue
}
```

```ts
// Cached data inside a handler (Cache Components): 'use cache' must live in a helper
import { cacheLife } from 'next/cache'

export async function GET() {
  return Response.json(await getProducts())
}
async function getProducts() {
  'use cache'
  cacheLife('hours')
  return await db.query('SELECT * FROM products')
}
```

Prerendering of a GET handler stops as soon as it touches: network/db/async-fs, `req.url`, `request.headers`, `request.cookies`, `request.body`, `cookies()`, `headers()`, `connection()`, or non-determinism (`Math.random()`). Special handlers (`sitemap.ts`, `opengraph-image.tsx`, `icon.tsx`) remain static by default.

### Auth in Client Components / context

React context works only in Client Components; child Server Components render first and can't see provider session data. If session data must reach the client, use React's `taintUniqueValue` to keep sensitive values off the client. Supabase is listed as a supported auth library (`supabase.com/docs/guides/getting-started/quickstarts/nextjs`).

### Misc

- `useFormStatus` in React 19 returns `data`, `method`, `action` in addition to `pending`.
- In Proxy, alternative cookie read: `req.cookies.get('session')?.value` (sync, on the request object).
- Prefer `redirects` config in `next.config.ts` for simple redirects; use Proxy only when you need request data/logic.

## data-server-client

Source: Next.js 16.2.10 bundled docs (`05-server-and-client-components.md`, `06-fetching-data.md`, `07-mutating-data.md`). These three files cover components, data fetching, and mutations only — route handlers, proxy/middleware, Tailwind, fonts, metadata, env details beyond `NEXT_PUBLIC_`, and build commands are NOT covered here.

### Differences vs Next.js 13/14/15 knowledge

- **`params` is a `Promise`** in pages/layouts and must be awaited: `{ params }: { params: Promise<{ id: string }> }` then `const { id } = await params`. Sync access is gone.
- **`cookies()` is async**: `const cookieStore = await cookies()` (from `next/headers`), then `.get('name')?.value` / `.set('name', 'v')` / `.delete('name')`. Set/delete only works in Server Actions (and triggers a server re-render of the current page + layouts so UI reflects the new cookie).
- **`fetch` is NOT cached by default** and blocks rendering until complete. Caching is opt-in via the **`use cache` directive** (new — replaces the old default-cached `fetch` / `revalidate` option mental model), or stream with `<Suspense>`. "Cache Components" is the new caching model and can emit **build-time errors** when a layout accesses runtime data without a boundary.
- **New `next/cache` exports**: `refresh()` (refreshes the client router after a mutation, does NOT revalidate tagged data) and `updateTag()` (alongside `revalidateTag`). `revalidatePath`/`revalidateTag`/`redirect` still exist with old semantics.
- **A layout that touches `cookies()`, `headers()`, or uncached fetch does NOT fall back to the same-segment `loading.js`** — it blocks navigation. Fix: wrap the access in its own `<Suspense>`, or move fetching into `page.js`.
- **`unstable_instant`**: verbatim AI-agent hint from the docs — "If client-side navigations feel slow, Suspense and streaming alone are not enough. Export `unstable_instant` from the route to ensure instant navigations. See docs/01-app/02-guides/instant-navigation.mdx"
- **`server-only` / `client-only` packages are optional to install** — Next.js handles these imports internally (npm package contents unused) and ships its own type declarations for them.
- Context syntax uses React 19 style: `<UserContext value={promise}>` (no `.Provider` needed; `.Provider` still shown in one example).
- Server Actions dispatch **sequentially** on the client ("The client currently dispatches and awaits them one at a time"); only POST can invoke them.
- Env vars: only `NEXT_PUBLIC_`-prefixed vars reach the client bundle; unprefixed vars are replaced with an **empty string** in client code.

### Verbatim warnings

> **[!WARNING]** Server Functions are reachable via direct POST requests, not just through your application's UI. Always verify authentication and authorization inside every Server Function.

> `fetch` requests are not cached by default and will block the page from rendering until the request is complete. Use the `use cache` directive to cache results, or wrap the fetching component in `<Suspense>` to stream fresh data at request time.

> Calling `redirect` throws a framework handled control-flow exception. Any code after it won't execute. If you need fresh data, call `revalidatePath` or `revalidateTag` beforehand.

> `React.cache` is scoped to the current request only. Each request gets its own memoization scope with no sharing between requests.

### Server Component page with async params (dynamic route)

```tsx
// app/[id]/page.tsx — Server Component (default), fetch data directly
export default async function Page({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const post = await getPost(id) // any async I/O: fetch, ORM, db client
  return <main><h1>{post.title}</h1></main>
}
```

DB/ORM queries are safe in Server Components (never bundled to client), but "You should still ensure requests are properly authenticated and authorized."

### Parallel fetching (avoid accidental waterfalls)

```tsx
export default async function Page({ params }: { params: Promise<{ username: string }> }) {
  const { username } = await params
  const artistData = getArtist(username)   // start, don't await
  const albumsData = getAlbums(username)
  const [artist, albums] = await Promise.all([artistData, albumsData])
  return <h1>{artist.name}</h1>
}
```

Use `Promise.allSettled` if one failure shouldn't fail all.

### Streaming: loading.tsx and Suspense

```tsx
// app/blog/loading.tsx — auto-wraps page.js in <Suspense>
export default function Loading() {
  return <div>Loading...</div>
}
```

```tsx
// Granular: stream only the slow part
import { Suspense } from 'react'
export default function BlogPage() {
  return (
    <main>
      <Suspense fallback={<BlogListSkeleton />}>
        <BlogList /> {/* async Server Component */}
      </Suspense>
    </main>
  )
}
```

Prefer `<Suspense>` close to uncached data access over `loading.js`, because layouts with runtime data (`cookies()`/`headers()`) bypass `loading.js` and block navigation.

### Stream a promise to a Client Component (`use` API)

```tsx
// Server: pass promise WITHOUT awaiting
export default function Page() {
  const posts = getPosts() // no await
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <Posts posts={posts} />
    </Suspense>
  )
}
```

```tsx
// Client
'use client'
import { use } from 'react'
export default function Posts({ posts }: { posts: Promise<{ id: string; title: string }[]> }) {
  const allPosts = use(posts)
  return <ul>{allPosts.map((p) => <li key={p.id}>{p.title}</li>)}</ul>
}
```

### Share per-request data (e.g. Supabase user) via React.cache + context

```ts

import { cache } from 'react'

  const res = await fetch('https://api.example.com/user')
  return res.json()

```

```tsx
// app/user-provider.tsx
'use client'
import { createContext } from 'react'
export const UserContext = createContext<Promise<User> | null>(null)
export default function UserProvider({ children, userPromise }: { children: React.ReactNode; userPromise: Promise<User> }) {
  return <UserContext value={userPromise}>{children}</UserContext>

```

```tsx
// app/layout.tsx — pass promise, don't await
import UserProvider from './user-provider'
import { getUser } from './lib/user'
export default function RootLayout({ children }: { children: React.ReactNode }) {
```


### Refresh vs revalidate after mutation

```ts
'use server'
import { refresh } from 'next/cache' // NEW in this version

export async function updatePost(formData: FormData) {
  // auth check + mutate ...
  refresh() // refreshes client router; does NOT revalidate tagged data
}
```

For tagged data use `updateTag` or `revalidateTag`; for path-based use `revalidatePath('/posts')`.

### Cookies in a Server Action (async!)

```ts
'use server'
import { cookies } from 'next/headers'

export async function exampleAction() {
  const cookieStore = await cookies()
  cookieStore.get('name')?.value
  cookieStore.set('name', 'Delba')   // triggers server re-render of page + layouts
  cookieStore.delete('name')
}
```

### Client vs Server component rules (unchanged but load-bearing)

- Pages/layouts are Server Components by default; `'use client'` at file top declares the boundary — everything it imports joins the client bundle.
- Server Components CAN be passed as `children`/props into Client Components (rendered on server, slotted in); they cannot be imported by client modules.
- Props crossing server→client must be serializable.
- React context is unsupported in Server Components — wrap providers in a `'use client'` file and render them deep (wrap `{children}`, not `<html>`).
- Guard server code with `import 'server-only'` (build-time error if imported client-side); `client-only` for window-touching modules. Installing the npm packages is optional.
- Client-component data fetching: React `use()` on a server-passed promise, or SWR/React Query.

## caching-revalidation

**Source: Next.js 16.2.10 bundled docs (`node_modules/next/dist/docs/`). Two caching worlds exist: the new Cache Components model (opt-in via `cacheComponents: true`) and the "Previous Model" (default when flag is off). Know which one the project uses before writing cache code.**

### Breaking changes vs Next 13/14/15

- **`fetch` is NOT cached by default.** The old `force-cache`-by-default behavior is gone. Opt in per request with `{ cache: 'force-cache' }` or `{ next: { revalidate: N } }`.
- **New in v16: Cache Components** (`cacheComponents: true` in `next.config.ts`) replaces the fetch-option/segment-config model with the `'use cache'` directive + `cacheLife()` / `cacheTag()`. Partial Prerendering (PPR) is the **default** behavior under this flag — no more `experimental_ppr`.
- **`revalidateTag` signature changed** (Cache Components mode): now takes a second "stale profile" argument — `revalidateTag('user', 'max')` is the recommended form (stale-while-revalidate semantics, serves stale while regenerating).
- **New API: `updateTag(tag)`** from `next/cache` — immediately expires cache (read-your-own-writes). **Server Actions only.** `revalidateTag` = SWR/background refresh, allowed in Server Actions and Route Handlers.
- **`cookies()`, `headers()`, `params`, `searchParams` are async.** `const cookieStore = await cookies()`; page props: `params: Promise<{ id: string }>` → `const { id } = await params`.
- **Runtime-API components must be wrapped in `<Suspense>`** under Cache Components — otherwise you get an `Uncached data was accessed outside of <Suspense>` error at dev/build time (docs message: "blocking-route").
- **Non-deterministic ops (`Math.random()`, `Date.now()`, `crypto.randomUUID()`) must be explicitly handled**: either `await connection()` (from `next/server`) first + `<Suspense>`, or cache them with `'use cache'`.
- **`GET` Route Handlers follow the same prerendering model as pages** when Cache Components is enabled.
- **`unstable_cache` is now legacy** — only for the previous (non-Cache-Components) model; replaced by `'use cache'`.
- Route segment configs (`export const dynamic/revalidate/fetchCache`) belong to the **previous model only** — don't mix with Cache Components.

### Model A: Cache Components (v16, opt-in)

Enable:
```ts
// next.config.ts
import type { NextConfig } from 'next'
const nextConfig: NextConfig = { cacheComponents: true }
export default nextConfig
```

Data-level caching (`'use cache'` at top of async function body; file-level `'use cache'` caches all exports; args + closed-over values form the cache key and must be serializable):
```ts
// app/lib/data.ts
import { cacheLife, cacheTag } from 'next/cache'

export async function getProducts() {
  'use cache'
  cacheLife('hours')
  cacheTag('products')
  return db.query('SELECT * FROM products')
}
```

UI-level caching (whole page/component):
```tsx
export default async function Page() {
  'use cache'
  cacheLife('hours')
  const users = await db.query('SELECT * FROM users')
  return <ul>{users.map((u) => <li key={u.id}>{u.name}</li>)}</ul>
}
```

`cacheLife` profiles (stale / revalidate / expire): `default` 5m/15m/never, `seconds` 30s/1s/60s, `minutes` 5m/1m/1h, `hours` 5m/1h/1d, `days` 5m/1d/1w, `weeks` 5m/1w/30d, `max` 5m/30d/1y. Custom: `cacheLife({ stale: 3600, revalidate: 7200, expire: 86400 })`. Short-lived caches (`seconds`, `revalidate: 0`, or `expire` < 5 min) are excluded from prerenders and become dynamic holes.

Fresh-per-request data (e.g. anything auth'd via Supabase cookies): **no `'use cache'`** — wrap in `<Suspense>`:
```tsx
import { cookies } from 'next/headers'
import { Suspense } from 'react'

async function UserGreeting() {
  const cookieStore = await cookies() // async!
  const theme = cookieStore.get('theme')?.value || 'light'
  return <p>Your theme: {theme}</p>
}

export default function Page() {
  return (
    <Suspense fallback={<p>Loading...</p>}>
      <UserGreeting />
    </Suspense>
  )
}
```

Pattern for per-user cached data — read cookie in an uncached component, pass value as prop into a cached one (prop becomes part of cache key):
```tsx
async function ProfileContent() {
  const session = (await cookies()).get('session')?.value
  return <CachedContent sessionId={session} />
}
async function CachedContent({ sessionId }: { sessionId: string }) {
  'use cache'
  const data = await fetchUserData(sessionId)
  return <div>{data}</div>
}
```

Server Action mutation + immediate revalidation (CRUD write path):
```ts
// app/lib/actions.ts
import { updateTag } from 'next/cache'
import { redirect } from 'next/navigation'

export async function createPost(formData: FormData) {
  'use server' // if inline; omit when file has 'use server' at top
  const post = await db.post.create({
    data: { title: formData.get('title'), content: formData.get('content') },
  })
  updateTag('posts')      // immediate expiry — user sees own write
  redirect(`/posts/${post.id}`)
}
```

Background/SWR revalidation (Server Action or Route Handler):
```ts
import { revalidateTag } from 'next/cache'
export async function updateUser(id: string) {
  // mutate...
  revalidateTag('user', 'max') // recommended: stale-while-revalidate; 2nd arg = stale window
}
```

Path-based (prefer tags — path over-invalidates):
```ts
import { revalidatePath } from 'next/cache'
revalidatePath('/profile')
```

| | `updateTag` | `revalidateTag` |
|---|---|---|
| Where | Server Actions only | Server Actions + Route Handlers |
| Behavior | Immediately expires | Stale-while-revalidate |
| Use case | Read-your-own-writes | Background refresh OK |

Unique-per-request values:
```tsx
import { connection } from 'next/server'
async function UniqueContent() {
  await connection() // defer to request time
  const uuid = crypto.randomUUID()
  return <p>Request ID: {uuid}</p>
}
// wrap in <Suspense>
```

Fully-dynamic app opt-out (kills static shell — use sparingly):
```tsx
// app/layout.tsx
<html>
  <Suspense fallback={null}>
    <body>{children}</body>
  </Suspense>
</html>
```

### Verbatim warnings worth heeding

- "When Cache Components is enabled, `GET` Route Handlers follow the same prerendering model as pages."
- "If you add `use cache` at the top of a file, all exported functions in the file will be cached."
- "By default, `use cache` stores entries in-memory. In serverless environments where memory doesn't persist across requests, `CachedContent` may re-evaluate on every request. Consider `'use cache: remote'` for durable, shared caching."
- "Prefer tag-based revalidation (`revalidateTag`/`updateTag`) over path-based when possible — it's more precise and avoids over-invalidating."
- "The revalidate value needs to be statically analyzable. For example `revalidate = 600` is valid, but `revalidate = 60 * 10` is not."
- "The revalidate value is not available when using `runtime = 'edge'`."
- "In Development, Pages are _always_ rendered on-demand and are never cached."
- "`<Suspense>` provides a fallback UI while async work completes, but it does not itself opt a component into dynamic rendering."
- Components that can't complete during prerendering and aren't `<Suspense>`-wrapped or `use cache`-marked → dev/build error: "Uncached data was accessed outside of `<Suspense>`".
- AI agent hint from docs: "To ensure client-side navigations are instant with Cache Components, export `unstable_instant` from the route." (see `docs/01-app/02-guides/instant-navigation.mdx`)
- Supabase-auth relevance: any component calling `cookies()` (i.e., every authed Supabase server client) is runtime-dynamic — never put `'use cache'` in it; wrap in `<Suspense>` and pass extracted values (user id, session) into cached functions if caching is desired.

## styling-fonts-metadata-errors

### Breaking changes / differences vs Next.js 13/14/15 (from these docs)

- **`error.tsx` / `global-error.tsx` prop renamed: `reset` → `unstable_retry`.** The error boundary component now receives `{ error, unstable_retry }: { error: Error & { digest?: string }; unstable_retry: () => void }`. Do NOT use `reset()`.
- **New component-level error boundary API: `unstable_catchError`** imported from `next/error` — wraps a fallback component into a reusable error boundary (see snippet below). This did not exist in 13/14/15.
- **`params` and `searchParams` are Promises** in `page.js`, `generateMetadata`, and metadata image files (`opengraph-image.tsx`) — must `await` them: `const { slug } = await params`. Type as `params: Promise<{ slug: string }>`.
- **Tailwind v4 is the default CSS setup**: no `tailwind.config.js|ts`, no `content` array, no `@tailwind base/components/utilities` directives. Setup is only the `@tailwindcss/postcss` plugin + `@import 'tailwindcss';` in globals.css. Tailwind v3 setup is relegated to a separate legacy guide ("If you need broader browser support for very old browsers, see the Tailwind CSS v3 setup instructions").
- **Streaming metadata**: for dynamically rendered pages, Next.js streams metadata separately after `generateMetadata` resolves (doesn't block UI). Disabled automatically for bots (Twitterbot, Slackbot, Bingbot) via User-Agent. Configure/disable via `htmlLimitedBots` option in `next.config`.
- **Default font is `Geist`** (from `next/font/google`) in examples, not Inter.
- Metadata `metadata` object / `generateMetadata` exports remain **Server Components only**.

### Error handling

**Expected errors in Server Actions — return values, not throw** ("avoid using `try`/`catch` blocks and throw errors. Instead, model expected errors as return values"):

```ts
// app/actions.ts
'use server'

export async function createPost(prevState: any, formData: FormData) {
  const title = formData.get('title')
  const res = await fetch('...', { method: 'POST', body: { title } })
  if (!res.ok) {
    return { message: 'Failed to create post' }
  }
}
```

Client consumption via `useActionState` (returns `[state, formAction, pending]`):

```tsx
'use client'
import { useActionState } from 'react'
import { createPost } from '@/app/actions'

export function Form() {
  const [state, formAction, pending] = useActionState(createPost, { message: '' })
  return (
    <form action={formAction}>
      <input type="text" name="title" required />
      {state?.message && <p aria-live="polite">{state.message}</p>}
      <button disabled={pending}>Create Post</button>
    </form>
  )
}
```

**404**: call `notFound()` from `next/navigation` in the page; sibling `not-found.tsx` renders the UI:

```tsx
import { notFound } from 'next/navigation'

export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params
  const post = getPostBySlug(slug)
  if (!post) notFound()
  return <div>{post.title}</div>
}
```

**Route-segment error boundary — NOTE `unstable_retry`, not `reset`:**

```tsx
// app/dashboard/error.tsx
'use client' // Error boundaries must be Client Components

import { useEffect } from 'react'

export default function ErrorPage({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string }
  unstable_retry: () => void
}) {
  useEffect(() => {
    console.error(error)
  }, [error])

  return (
    <div>
      <h2>Something went wrong!</h2>
      <button onClick={() => unstable_retry()}>Try again</button>
    </div>
  )
}
```

**Component-level error boundary (new API)**:

```tsx
// app/custom-error-boundary.tsx
'use client'

import { unstable_catchError as catchError, type ErrorInfo } from 'next/error'

function ErrorFallback(
  props: { title: string },
  { error, unstable_retry }: ErrorInfo
) {
  return (
    <div>
      <h2>{props.title}</h2>
      <p>{error.message}</p>
      <button onClick={() => unstable_retry()}>Try again</button>
    </div>
  )
}

export default catchError(ErrorFallback)
// usage: <ErrorBoundary title="Dashboard Error">{children}</ErrorBoundary>
```

**Global errors** (`app/global-error.tsx`): `'use client'`, receives `{ error, unstable_retry }`, and MUST render its own `<html>` and `<body>` tags (replaces root layout when active).

Error boundary gotchas:
- Error boundaries don't catch errors in event handlers or async code (catch manually, store with `useState`).
- Unhandled errors inside `startTransition` from `useTransition` DO bubble to the nearest error boundary.
- Errors bubble to the nearest parent `error.tsx`; nest them per segment for granularity.

### Environment variables

- `.env*` files load into `process.env` automatically. Load order (first hit wins): `process.env` → `.env.$(NODE_ENV).local` → `.env.local` (skipped when `NODE_ENV=test`) → `.env.$(NODE_ENV)` → `.env`.
- Allowed `NODE_ENV` values: `production`, `development`, `test`. Unset → `development` for `next dev`, `production` for everything else.
- If using `src/`, `.env*` files stay in the **project root**, not `src/`.
- Server-only by default. Browser exposure requires `NEXT_PUBLIC_` prefix — **inlined at `next build` time**, frozen thereafter (matters for single-Docker-image-multi-env promotion; use the `connection()` pattern above for runtime values). Dynamic lookups (`process.env[varName]`, `const env = process.env`) are NOT inlined.
- `$VAR` expansion inside `.env` files is supported; escape literal `$` as `\$`. Multiline values supported (real line breaks or `\n` inside double quotes).
- Verbatim warning: "The default `create-next-app` template ensures all `.env` files are added to your `.gitignore`. You almost never want to commit these files to your repository."
- Loading env outside the Next runtime (ORM config, Jest setup):
  ```ts
  // envConfig.ts
  import { loadEnvConfig } from '@next/env'
  loadEnvConfig(process.cwd())
  ```
- `.env.test` for the test environment (commit it; never commit `.env*.local`). `.env.local` is NOT loaded when `NODE_ENV=test`.
- Route Handler reading env (server-side, safe):
  ```js
  // app/api/route.js
  export async function GET() {
    const db = await myDB.connect({
      host: process.env.DB_HOST,
      username: process.env.DB_USER,
      password: process.env.DB_PASS,
    })
  }
  ```
- Run code on server startup via the `register` function (instrumentation).
